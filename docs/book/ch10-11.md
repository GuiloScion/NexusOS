# Chapter 10. Graphics: the framebuffer, fonts, and a console

So far everything has been text. Now we go graphical, and it turns out drawing a pixel is *easier* than you would expect. The hard part is getting the hardware into a mode where a pixel is just a memory write.

## The idea: a linear framebuffer

In graphics mode, the screen is a big array in memory called the **framebuffer**. Each pixel is a few bytes (3 for 24-bit colour, 4 for 32-bit). To light up a pixel you just write its colour to the right address. No drawing commands, no GPU API, just memory.

The screen is laid out row by row. The address of pixel `(x, y)` is:

```text
addr = framebuffer_base + y * pitch + x * (bytes_per_pixel)
```

Two things trip everyone up:

- **Pitch, not width.** `pitch` (a.k.a. stride) is the number of *bytes* per row. It is often **larger** than `width * bytes_per_pixel` because rows can be padded for alignment. Always use the pitch the firmware reports; never assume `width * bpp`.
- **Byte order.** 24-bit colour is usually stored **B, G, R** in memory, not R, G, B. Get it backwards and your reds and blues swap.

NexusOS's `fb_putpixel` packs both lessons into half a dozen lines:

*Listing 10.1. `kernel/fb.c`, lines 50–60: the canonical "write one pixel" routine.*

```c
void fb_putpixel(uint32_t x, uint32_t y, uint32_t color) {
    if (!fb.active || x >= fb.width || y >= fb.height) return;
    uint8_t *p = fb.addr + (uint64_t)y * fb.pitch + (uint64_t)x * (fb.bpp / 8);
    if (fb.bpp == 32) {
        *(uint32_t *)p = color;
    } else {                       /* 24 bpp */
        p[0] = (uint8_t)(color & 0xFF);
        p[1] = (uint8_t)((color >> 8) & 0xFF);
        p[2] = (uint8_t)((color >> 16) & 0xFF);
    }
}
```

The fact that the same code handles both 24-bpp and 32-bpp framebuffers (they happen on different hardware) is exactly the kind of "small abstraction at the boundary" that keeps the rest of the codebase clean.

## Getting into a graphics mode (VESA/VBE)

A modern card can do graphics, but *asking* it to is a BIOS service called **VBE** (VESA BIOS Extensions), and BIOS services only work in **real mode**, before we jump to the kernel. So the *bootloader* sets the mode.

In NexusOS, `bootloader/boot.asm` (still in 16-bit real mode) calls:

- `int 0x10, AX=0x4F01`, *get mode info* for a 1024×768 mode, which returns the framebuffer's physical address, pitch, dimensions, and bits-per-pixel.
- `int 0x10, AX=0x4F02`, *set* that mode, with the "linear framebuffer" bit.

It then writes a small descriptor (address, pitch, width, height, bpp, and a "valid" flag) at a known low-memory address (`0x9700`) for the kernel to read after the mode switch. If VBE fails, the descriptor's valid flag is set to 0 and the kernel falls back to its text console.

The kernel reads the descriptor and identity-maps the framebuffer range page by page so it can be touched directly:

*Listing 10.2. `kernel/fb.c`, lines 12–44: read the bootloader's descriptor and map the framebuffer.*

```c
#define FB_INFO_ADDR 0x9700

bool fb_init(void) {
    volatile uint32_t *info = (volatile uint32_t *)(uintptr_t)FB_INFO_ADDR;

    uint32_t lfb    = info[0];
    uint32_t pitch  = info[1];
    uint32_t width  = info[2];
    uint32_t height = info[3];
    uint32_t bpp    = info[4];
    uint32_t valid  = info[5];

    if (!valid || lfb == 0 || width == 0 || height == 0) {
        fb.active = false;
        return false;
    }

    /* The framebuffer lives above identity-mapped RAM, so map it in
     * explicitly. Identity-map (virt == phys) one page at a time. */
    uint64_t size = (uint64_t)pitch * height;
    for (uint64_t off = 0; off < size; off += 0x1000) {
        if (!vmm_map((uintptr_t)lfb + off, (uintptr_t)lfb + off, PTE_KERNEL_RW)) {
            fb.active = false;
            return false;
        }
    }

    fb.addr   = (uint8_t *)(uintptr_t)lfb;
    fb.pitch  = pitch;
    fb.width  = width;
    fb.height = height;
    fb.bpp    = bpp;
    fb.active = true;
    return true;
}
```

The framebuffer's physical address is typically *high* (NexusOS sees `0xFD000000` in QEMU), above the RAM your paging identity-mapped in Chapter 7. It is memory-mapped I/O, not RAM, so the kernel must map those pages explicitly before touching them. That is what the loop does.

> **Pitfall:** the moment you switch to a graphics mode, the old VGA *text* buffer at `0xB8000` stops showing anything. So switching modes and having something to draw must come together; otherwise you get a black screen and think you have crashed. (Keep the serial port as your debug lifeline.)

## Drawing: surfaces and primitives

You do not want every drawing routine hard-coded to "the screen." NexusOS uses a **surface** abstraction (`kernel/gfx.c`): a `surface_t` is *any* pixel buffer (the real screen, or an off-screen buffer) described by its address, pitch, size, and bpp. Every primitive (`gfx_pixel`, `gfx_fill`, `gfx_blit`, `gfx_glyph`, `gfx_text`) takes a surface, so the same code draws to the screen or to a back buffer.

*Listing 10.3. `kernel/gfx.c`, lines 19–41: the rectangle fill, which is a row loop wrapped around the pixel write.*

```c
void gfx_fill(const surface_t *s, int x, int y, int w, int h, uint32_t color) {
    int x0 = x < 0 ? 0 : x;
    int y0 = y < 0 ? 0 : y;
    int x1 = x + w, y1 = y + h;
    if (x1 > (int)s->width)  x1 = (int)s->width;
    if (y1 > (int)s->height) y1 = (int)s->height;
    int bytes = s->bpp / 8;
    for (int yy = y0; yy < y1; yy++) {
        uint8_t *row = s->addr + (uint64_t)yy * s->pitch + (uint64_t)x0 * bytes;
        if (s->bpp == 32) {
            uint32_t *px = (uint32_t *)row;
            for (int xx = x0; xx < x1; xx++) *px++ = color;
        } else {
            uint8_t *px = row;
            for (int xx = x0; xx < x1; xx++) {
                px[0] = (uint8_t)(color & 0xFF);
                px[1] = (uint8_t)((color >> 8) & 0xFF);
                px[2] = (uint8_t)((color >> 16) & 0xFF);
                px += 3;
            }
        }
    }
}
```

The surface abstraction pays off hugely in the next chapter, where the window manager allocates an off-screen back buffer the same size as the screen and composes the whole desktop into it.

## Text without the BIOS: a bitmap font

In graphics mode there is no "print character" anymore; you draw letters yourself. A **bitmap font** is just an array: for each character, 8 bytes, where each byte is a row and each bit is a pixel (`1` = draw, `0` = skip). NexusOS embeds a public-domain 8×8 font in `kernel/font8x8.h`; `gfx_glyph` reads those bits and fills a (scaled) block per set bit.

## A console on the framebuffer

To replace the text console, NexusOS keeps a **character grid** in `kernel/fbcon.c`: a 2D array of characters plus a cursor. `console_*` writes update the grid (handling newline, backspace, scroll); a separate render step draws the grid using the font.

Storing the console as *data* (not as pixels you drew once) is the key trick. It means the screen can be **re-rendered at any time** from the grid, which is exactly what a compositor needs. A version counter ticks each time the grid changes; the compositor in Chapter 11 watches that counter to know when to redraw.

You can now draw pixels, text, and rectangles to an off-screen surface and blit it to the screen. That is everything you need to build a **windowing GUI**: windows, a mouse cursor, and a compositor. That is the next chapter.

## Exercises

1. **Smoke test: three rectangles on a colour background.** From `kernel_main`, after `fb_init`, call `gfx_fill(screen, 0, 0, w, h, 0x202030)` to set a dark blue background, then three more `gfx_fill`s in red, green, and blue at different positions. This was NexusOS's first graphics commit; if it works for you, every drawing routine in the rest of the chapter is going to work.

   *Hint:* Use `const surface_t *screen` constructed from `fb_get()`. Pick colours like `0xFF4040` (red), `0x40C040` (green), `0x4080FF` (blue); they look better than full-saturation primaries on most monitors.

2. **Draw a string at multiple scales.** Use `gfx_text(screen, x, y, "Hello, framebuffer!", fg, bg, scale)` to render the same string at scale 1, 2, and 4. At scale 4 each pixel of the font becomes a 4×4 block, so the text is huge but readable.

   *Hint:* The font is 8×8, so scale 1 produces 8-pixel-tall characters and scale 4 produces 32-pixel-tall ones. If you read `gfx_glyph` you will see that the implementation is `gfx_fill(s, x + col*scale, y + row*scale, scale, scale, fg)` per set bit: a `gfx_fill` per "pixel" of the font, scaled up.

3. **Save the screen as an image without a monitor.** QEMU's monitor command `screendump out.ppm` writes the framebuffer to a PPM file. From the command line: `qemu-system-x86_64 -monitor stdio …` and type `screendump nexusos.ppm` at the `(qemu)` prompt. This is invaluable for headless or CI testing; you can verify your graphics work without anyone looking at a screen.

   *Hint:* NexusOS automates this in `tools/screenshot.sh`: it launches QEMU with `-monitor unix:./qmp.sock`, waits for the kernel banner on serial, then sends the `screendump` over the socket. The result is a PPM you can convert to PNG with `convert nexusos.ppm nexusos.png`.

4. **Build a simple drawing API.** Write `draw_line(surface, x0, y0, x1, y1, color)` using Bresenham's algorithm, the classic integer-only line draw. Then `draw_circle` using the midpoint algorithm. You will use both in the window manager for the title bar separator and for the close button's `X`.

   *Hint:* Bresenham's is *all* integer arithmetic; the trick is to step in the major axis and accumulate an error term that flips a step in the minor axis when it crosses a threshold. Both algorithms fit in a dozen lines each and are in any graphics textbook.

# Chapter 11. A window manager: the mouse, a compositor, and windows

This is the chapter where it stops looking like a kernel and starts looking like a *computer*. We will add a mouse, then build a **compositor** that draws overlapping windows with a cursor on top: the heart of any graphical desktop.

## The mouse (PS/2, IRQ12)

The PS/2 mouse is the keyboard's sibling. It lives on the 8042 controller's *second* port, fires **IRQ12**, and sends 3-byte packets:

- **Byte 0:** button states (left/right/middle), sign bits for X and Y, X/Y overflow flags, and a marker bit that is always 1.
- **Byte 1:** X movement (signed; the sign bit is byte 0).
- **Byte 2:** Y movement (signed, and positive means *up*, so you subtract it from your screen Y).

The packet-assembly logic is small but easy to get wrong:

*Listing 11.1. `kernel/mouse.c`, lines 55–71: assembling 3 bytes into a movement.*

```c
static void mouse_process(void) {
    if (packet[0] & 0xC0) return;          /* X/Y overflow -- drop */

    int dx = (int)packet[1] - (int)((packet[0] << 4) & 0x100);
    int dy = (int)packet[2] - (int)((packet[0] << 3) & 0x100);

    buttons = packet[0] & 0x07;

    mx += dx;
    my -= dy;                              /* screen Y grows downward */

    const framebuffer_t *f = fb_get();
    int32_t maxx = (int32_t)f->width  - 1;
    int32_t maxy = (int32_t)f->height - 1;
    if (mx < 0) mx = 0; else if (mx > maxx) mx = maxx;
    if (my < 0) my = 0; else if (my > maxy) my = maxy;
}
```

The bit-arithmetic dance for `dx`/`dy` is just sign-extension: byte 1 is a 9-bit two's-complement value with the high bit kept in byte 0; we reconstruct the sign by subtracting `0x100` if that bit was set.

> **Pitfall:** the marker bit in byte 0 lets you re-sync if you ever read a byte mid-packet. If your cursor jumps wildly, you have lost packet alignment; check that bit and drop the byte if it is wrong.

## The naive approach (and why it fails)

The obvious way to draw a cursor: save the pixels under it, draw the arrow, and when it moves, restore the saved pixels and repeat. This *works* until something else draws on the screen underneath the cursor; then your "restore" paints stale pixels back over the new content. You get trails and corruption. NexusOS shipped this in an early version and immediately felt the pain.

## The fix: a compositor with a back buffer

The professional approach is **double buffering and compositing**:

1. Keep an **off-screen back buffer** the same size as the screen (allocate it from your heap; for 1024×768 that is ~2.4 MB).
2. To draw a frame, **compose** the whole scene into the back buffer from scratch: desktop background, then each window in z-order.
3. **Present**: blit the back buffer to the real framebuffer in one shot, then draw the mouse cursor on top.

Because you rebuild the scene every frame from a *model* (window list, console grid), nothing is ever stale. And because the cursor is painted *after* the blit and never stored in the scene, **it can never clobber what is underneath**. The trails problem simply disappears.

NexusOS runs the compositor as its own scheduler task: it recomposes when something changed (a "dirty" flag, plus a version counter on the console grid) and presents every frame so the cursor stays responsive.

## Windows as data

A window is just a struct: position, size, title, z-order, a few flags (minimised, closable), and its contents. The window manager keeps a list and a **z-order**. Composing is then: for each window from back to front, draw its border, title bar (highlighted if focused), and body.

*Listing 11.2. `kernel/wm.c`, lines 25–35: the window struct, fewer fields than you might expect.*

```c
typedef struct {
    int  x, y, w, h;            /* h is body height (title bar is extra) */
    const char *title;
    const char *const *lines;
    int  nlines;
    uint32_t body;
    bool is_terminal;
    bool closable;
    bool minimized;
    bool used;
} window_t;
```

That is the entire model. Everything visual is derived from these fields at compose time. Interaction falls out of hit-testing the mouse against this list:

- **Click:** find the top-most window under the cursor, raise it to the front, give it focus.
- **Drag the title bar:** move that window with the mouse delta.
- **Close / minimise buttons:** small rectangles in the title bar that you hit-test.
- **Taskbar:** a strip with a button per window (and a clock); clicking restores or raises.

None of this needs new graphics primitives. It is all rectangles and text on a surface, plus a little geometry.

## Putting the shell in a window

Remember the console is a **character grid** (Chapter 10)? The compositor can render that grid *inside a window's body* instead of full-screen. Now the shell lives in a draggable "Terminal" window, and the rest of the screen is a desktop with other windows. That is NexusOS's default desktop.

The cursor itself is an old-school bitmap. Read it as art:

*Listing 11.3. `kernel/wm.c`, lines 54–59: the arrow cursor, in ASCII.*

```c
#define CUR_H 19
static const char *const arrow[CUR_H] = {
    "X", "XX", "X.X", "X..X", "X...X", "X....X", "X.....X", "X......X",
    "X.......X", "X........X", "X.........X", "X......XXXXX", "X...X..X",
    "X..XX..X", "X.X  X..X", "XX   X..X", "X     X..X", "      X..X", "       XX",
};
```

`X` is the outline (drawn black), `.` is the interior (drawn white), space is transparent. Rendering is a loop: for each row, for each character, paint a 1×1 pixel of the matching colour, or skip if it is a space. That is the entire mouse cursor: twenty lines of source.

You have a graphical, interactive OS in an emulator. The real test is booting it on a physical machine, where the firmware fights back. That is the next chapter, and it is where the most valuable lessons live.

## Exercises

1. **Add a fourth window with your own text.** Edit `wm.c` to register a new window, give it a title, and pass an array of `const char *` lines for its body. Drag it over the others; confirm no artifacts. That visual proof is your compositor working: if you saw smearing or stale pixels, the back-buffer recompose has a bug.

   *Hint:* The existing windows are registered in NexusOS's startup. Mirror one of those calls and run; you should see your window appear at the chosen position with the title you gave.

2. **Drive the mouse from a script.** QEMU's monitor can inject mouse motion and clicks via `input-send-event`. Combine with `screendump` from Chapter 10's exercises to take an automated screenshot after a scripted click ("open a window, drag it, close it, verify the desktop is restored"). NexusOS uses exactly this to test the window manager without a human.

   *Hint:* The QEMU monitor syntax is roughly `input-send-event mouse-button left-down; input-send-event mouse-button left-up`. Inject between two `screendump` calls so you can see the before-and-after.

3. **Give windows a resize handle.** Add a small triangular hit zone in the bottom-right corner of each window. On click-and-drag there, update the window's `w` and `h`. Confirm the compositor redraws cleanly: if the back buffer is the right size, it just works; if you cached anything dimensioned to the old size (e.g. a per-window cached glyph cache), you will have a bug to fix.

   *Hint:* Hit-testing the resize handle is `if (mx >= win.x + win.w - 12 && my >= win.y + win.h - 12)`. The drag state is the same shape as title-bar drag: remember the starting mouse position and starting window dimensions, update on each frame.

4. **Add a second terminal.** Create a second window with `is_terminal = true`. The compositor will render that window's body as the console grid, so you have two terminals showing the same shell. (Or wire them to separate consoles, if you have built a multi-console kernel.) This exercise illustrates why the console grid being *data* matters: any window can render it.

   *Hint:* If both terminals show the same content, they share the global console, which is fine for a demo but exposes the next refactor: making the console a per-window object. That is one step toward real per-process I/O.
