# Chapter 3. How a PC boots: BIOS, real mode, and the bootloader

## What happens when you press power

On a legacy/BIOS PC, the sequence is fixed and short:

1. The CPU powers on in **16-bit real mode**, the ancient mode of the original 1978 8086, for backward compatibility. Only 1 MiB of memory is addressable, and there is no memory protection of any kind.
2. The **BIOS** (firmware on the motherboard) runs. It tests hardware, initialises devices it knows about, then looks for a bootable device.
3. It reads the first **512-byte sector** (the *boot sector*, or *MBR* if you treat the whole disk that way) of that device into memory at physical address **`0x7C00`** and jumps to it, *if and only if* the last two bytes of that sector are the signature `0x55 0xAA`.
4. Your code is now running. You have 512 bytes, and the BIOS's help (via *software interrupts*), to bootstrap everything else.

That is why our boot sector in the previous chapter declared `[ORG 0x7C00]` (where it expects to live), `[BITS 16]` (the CPU's current mode), and `dw 0xAA55` at the end (the signature).

## Real mode and "segment:offset"

In real mode, every address is formed as `segment * 16 + offset`. The segment registers (`cs`, `ds`, `es`, `ss`) hold the segment; the instruction pointer or your operands provide the offset. It is clunky, but for our purposes you mostly set the segments to zero and use flat offsets. NexusOS's bootloader does exactly that at the top of `bootloader/boot.asm`:

*Listing 3.1. `bootloader/boot.asm`, lines 12–19: setting up segments and a stack.*

```asm
start:
    cli                         ; no interrupts while we set up
    xor ax, ax
    mov ds, ax                  ; ds = es = ss = 0  (flat addressing)
    mov es, ax
    mov ss, ax
    mov sp, 0x7C00              ; stack grows downward from our load addr
    sti
```

`cli` disables interrupts; `sti` re-enables them. The reason we bracket the segment setup with `cli`/`sti` is that an interrupt firing while `ss` is being assigned but `sp` has not yet been set could push to a wild address. It is paranoia, but cheap paranoia.

The choice of `sp = 0x7C00` puts the stack immediately *below* the boot sector itself; the stack grows downward into otherwise-unused memory and the code lives upward from `0x7C00` for 510 bytes. Tidy.

## The BIOS is a free toolkit (while it lasts)

In real mode you can call BIOS services with the `int` instruction. Three of them matter at boot:

- **`int 0x10` (video).** With `ah = 0x0E`, it prints the character in `al` to the screen ("teletype"). That is how the bootloader prints `Booting NexusOS...`.
- **`int 0x13` (disk).** Reads sectors from the boot device into memory.
- **`int 0x15, ax = 0xE820` (system).** Returns the **memory map**: which physical address ranges are usable RAM and which are reserved for firmware, MMIO, or ACPI tables. The kernel needs this later, and crucially, this service is **only available in real mode**. The bootloader has to grab the map *now* and stash it somewhere the kernel can find it.

> **Important:** the moment you leave real mode (next chapter), the BIOS is gone. Anything you need from it (the memory map, a video mode, the disk's geometry) you must collect *first*.

## What a bootloader actually does

512 bytes is tiny, so the bootloader's job is narrow: *set up just enough, then load and jump to the real kernel.* NexusOS's MBR does five things:

1. Saves the boot drive number the BIOS handed it in `dl`.
2. Collects the **E820 memory map** and stores the result at physical `0x9000`.
3. Optionally sets a **VESA graphics mode** via the video BIOS (Chapter 10 unpacks this).
4. **Loads the kernel** from disk to `0x10000`.
5. Switches the CPU to protected mode, then long mode, and jumps to the kernel.

### Loading the kernel from disk

The classic way to read sectors is `int 0x13, ah = 0x02` (CHS addressing: cylinder, head, sector). It works in QEMU. **On real hardware booting from USB it often hangs**, because CHS geometry is a fiction for modern devices: there is no platter and no head. NexusOS uses the **LBA extensions** (`int 0x13, ah = 0x42`) with a *Disk Address Packet* instead. This is a flat "give me N sectors starting at LBA X" request that every USB-boot BIOS supports.

*Listing 3.2. `bootloader/boot.asm`, lines 95–102 and 157–165: the kernel load.*

```asm
    ; Load kernel to 0x10000 (int 13h LBA).
    ; CHS reads hang on many real USB-boot BIOSes; the LBA extensions
    ; are universally available on anything that can boot from USB.
    mov si, kernel_dap
    mov dl, [boot_drive]
    mov ah, 0x42
    int 0x13
    jc  disk_error

; ... elsewhere in the file ...

; Disk Address Packet for the int 13h LBA read of the kernel.
align 4
kernel_dap:
    db 0x10                     ; packet size, always 16
    db 0                        ; reserved
    dw 127                      ; sectors to read (kernel is ~73)
    dw 0x0000                   ; destination offset
    dw 0x1000                   ; destination segment -> phys 0x10000
    dq 1                        ; start LBA (sector 0 is the MBR itself)
```

`jc disk_error` is the only error handling we can afford in 512 bytes: on carry (the BIOS convention for failure), we print a message and halt. Notice we load 127 sectors even though the kernel is only ~73; the extras are zero-padded, so reading them is harmless and the over-read insulates against the kernel growing slightly without us having to rebuild the bootloader.

This is a real lesson NexusOS learned the hard way on an ASUS desktop. Chapter 12 has the full story.

## Where things live in low memory

A handy mental map of the first megabyte while booting:

| Address       | What's there                              |
| ------------- | ----------------------------------------- |
| `0x07C00`     | Your boot sector (loaded by BIOS)         |
| `0x09000`     | (NexusOS) E820 memory map we saved        |
| `0x09700`     | (NexusOS) framebuffer descriptor          |
| `0x10000`     | Where we load the kernel                  |
| `0x70000`     | (NexusOS) early page tables               |
| `0x90000`     | (NexusOS) early stack                     |
| `0xB8000`     | VGA text-mode screen memory               |

These are all hand-picked locations that have to dodge BIOS data and each other. They are arbitrary in the sense that any free address would do, but you cannot change one without checking that nothing else expects it.

You now know what the BIOS does for you and what it stops doing the moment you leave real mode. Next: leaving real mode for good, on the way to 64-bit.

## Exercises

1. **Print a string with a loop.** Take your boot sector from Chapter 2 and extend it to print a 10-character message using a loop and a string. (This is exactly the print routine NexusOS uses to say `Booting NexusOS...`.) The body is the same `lodsb / test / jz / int 0x10` pattern. Declare your string with `db "Hi there!", 0`.

   *Hint:* The full routine NexusOS uses is `print_string: mov ah, 0x0E; mov bx, 0x0007; .loop: lodsb; test al, al; jz .done; int 0x10; jmp .loop; .done: ret`. The `mov bx, 0x0007` sets the BIOS attribute byte (light grey on black); without it, on some firmware the colour is unspecified.

2. **Read a second sector and jump to it.** Write a small "stage 2", a second 512-byte program that prints something different, and place it at LBA 1 of your disk image. From your boot sector, use `int 0x13 ah=0x02` (CHS) or `ah=0x42` (LBA) to read that sector into, say, `0x8000`, then `jmp 0x0000:0x8000`. This is, in miniature, what every bootloader on Earth does.

   *Hint:* For LBA, copy NexusOS's Disk Address Packet structure but change the segment/offset to `0x0000:0x8000` and the sector count to `1`. To build the test disk, concatenate the two binaries: `cat boot.bin stage2.bin > disk.img`, then run QEMU on `disk.img`.

3. **Collect the E820 map yourself.** Add the E820 loop from `bootloader/boot.asm` (lines 25–53) to your boot sector and print the number of entries the BIOS returned. You will find QEMU returns five to seven entries, depending on configuration. Each is 24 bytes describing one range of physical memory: base, length, type (1 = usable RAM, other values = reserved). Save the count at `[0x9000]` so a future kernel can find it.

   *Hint:* The E820 loop is the most fiddly piece of real-mode code in the bootloader, because the BIOS interface is awkward. The key bits: set `eax = 0xE820`, `edx = 0x534D4150` (the ASCII bytes of "SMAP"), `ecx = 24`, point `es:di` at the buffer, and call `int 0x15`. On the first call set `ebx = 0`; on subsequent calls leave `ebx` as the BIOS returned it. End when carry is set or `ebx` comes back zero.

4. **Make a stage 2 that prints the E820 map.** Combine exercises 2 and 3: stage 1 grabs E820, stage 2 reads it from `0x9000` and prints each entry's base, length, and type. Now you can *see* your RAM layout. This is exactly what the kernel does in Chapter 7 to build its physical memory allocator.

   *Hint:* Stage 2 is bigger than 512 bytes if you do this in any reasonable way, so you will want a third stage. Or, better, switch to 32-bit code now and write the rest in C. Doing that is the entire next chapter.

That second step, *load more code and jump to it,* is the heart of bootloading. Once you can do that reliably, you are ready to leave the cramped 16-bit world behind.

# Chapter 4. From 16-bit to 64-bit: protected mode, paging, and long mode

The CPU boots in 16-bit real mode for compatibility, but we want the full 64-bit machine: all of RAM, memory protection, and modern instructions. Getting there is a fixed three-step ritual. It looks intimidating; it is actually just a checklist.

## The three modes

- **Real mode (16-bit):** where we start. 1 MiB addressable, BIOS available, no protection.
- **Protected mode (32-bit):** 4 GiB addressable, segmentation and protection, paging available. A stepping stone.
- **Long mode (64-bit):** the goal. Requires paging to be enabled. This is where the kernel runs.

You must go real → protected → long. You cannot skip to long mode directly; the CPU literally does not allow it.

## Step 1: A20 and the GDT

**The A20 line.** For historical reasons (a 1985-era compatibility hack with the original 8086), the 21st address line is *disabled* at boot and memory wraps at 1 MiB. To use memory above 1 MiB, you must enable it. The simplest method, the "fast A20" gate via the system control port, is two instructions:

*Listing 4.1. `bootloader/boot.asm`, lines 105–107: enabling the A20 line.*

```asm
    in  al, 0x92
    or  al, 2                   ; set bit 1: A20 enable
    out 0x92, al
```

There are older, more involved A20-enabling sequences via the 8042 keyboard controller; on every PC this book targets, the port `0x92` method works.

**The GDT (Global Descriptor Table).** Protected mode replaces real mode's segment math with *descriptors* that define memory regions and their permissions. For a flat memory model, where every segment covers all of RAM, you need only a handful of entries: a null descriptor (required by the architecture), a 32-bit code segment, a 32-bit data segment, and (for long mode) a 64-bit code segment.

*Listing 4.2. `bootloader/boot.asm`, lines 167–177: a minimal GDT and its descriptor.*

```asm
align 8
gdt_start:
    dq 0x0000000000000000       ; null  (required)
    dq 0x00CF9A000000FFFF       ; 32-bit code, ring 0, base=0, limit=4 GiB
    dq 0x00CF92000000FFFF       ; 32-bit data, ring 0, base=0, limit=4 GiB
    dq 0x00AF9A000000FFFF       ; 64-bit code, ring 0
gdt_end:

gdt_descriptor:
    dw gdt_end - gdt_start - 1
    dd gdt_start
```

Those magic numbers are just permission, limit, and granularity bits packed into a 64-bit descriptor; you can copy a known-good GDT and move on with your life. The numerical offsets you will reference (`0x08` for the 32-bit code segment, `0x10` for data, `0x18` for the 64-bit code segment) match each descriptor's byte offset inside the table. Load it with `lgdt [gdt_descriptor]`.

## Step 2: enter protected mode

Set bit 0 of control register `cr0` ("PE", for Protected mode Enable), then *far-jump* to flush the CPU's instruction prefetch and load the new code-segment selector:

*Listing 4.3. `bootloader/boot.asm`, lines 109–116: the jump into protected mode.*

```asm
    cli
    lgdt [gdt_descriptor]

    mov eax, cr0
    or  eax, 1                  ; CR0.PE = 1
    mov cr0, eax

    jmp 0x08:protected_mode     ; 0x08 = our 32-bit code selector
```

You are now in 32-bit protected mode. The reason the jump is necessary, rather than letting execution fall through, is that the CPU caches a "shadow" copy of each segment descriptor, and only a far jump (or an interrupt return) reloads that shadow with the new GDT's contents. Without the jump, the next instruction would still execute under the old segment cache, with chaotic consequences.

## Step 3: paging, then long mode

64-bit long mode **requires paging** to be enabled before it can be entered. Paging is the mechanism that maps *virtual* addresses (what code uses) to *physical* addresses (actual RAM), and it is the foundation of all memory management; Chapter 7 is dedicated to it. To get into long mode, you only need a *minimal* set of page tables: enough to map the kernel so it can execute its first few instructions.

x86-64 paging is a four-level tree (PML4 → PDPT → PD → PT), each level a table of 512 entries. A simple bootstrap maps the first 2 MiB of memory with a single "huge" 2 MiB page. NexusOS does this in `kernel/kernel_entry.asm`, on the way in from the bootloader:

*Listing 4.4. `kernel/kernel_entry.asm`, lines 17–49: the bootstrap page tables and the long-mode jump.*

```asm
[BITS 32]
_start:
    cli

    ; Zero 16 KiB of page-table scratch at 0x70000.
    mov edi, 0x70000
    xor eax, eax
    mov ecx, 0x4000 / 4
    rep stosd

    ; PML4[0] -> PDPT
    mov dword [0x70000], 0x71000 | 0x03
    ; PDPT[0] -> PD
    mov dword [0x71000], 0x72000 | 0x03
    ; PD[0] -> 2 MiB page at 0x0  (PS=1 in flags)
    mov dword [0x72000], 0x00000000 | 0x83

    mov eax, 0x70000
    mov cr3, eax                ; CR3 points the CPU at the page tables

    mov eax, cr4
    or  eax, 1 << 5             ; CR4.PAE (physical address extension)
    mov cr4, eax

    mov ecx, 0xC0000080         ; the EFER model-specific register
    rdmsr
    or  eax, 1 << 8             ; EFER.LME = long mode enable
    wrmsr

    mov eax, cr0
    or  eax, 1 << 31            ; CR0.PG = paging on  -> now in long mode
    mov cr0, eax

    jmp 0x18:long_mode          ; 0x18 = our 64-bit code selector
```

After that far jump you are executing 64-bit code. The `| 3` on the non-leaf entries sets `present | writable`; the `| 0x83` on the leaf adds the `PS` ("page size") bit that tells the CPU "this is a 2 MiB page, do not walk further."

A note on why `_start` is the first symbol in the kernel binary: the bootloader will jump to physical address `0x10000`, and our linker script (Listing 5.2 in the next chapter) places `_start` exactly there. Reorder the kernel file list or rename the symbol, and the kernel becomes unbootable.

## Why two stages of page tables?

This bootstrap only maps the first 2 MiB, just enough to run the kernel's entry code. Once the kernel is up and has a *physical memory allocator* (Chapter 7), it builds real page tables covering all of RAM and switches `CR3` to those. It is a classic pattern: hand-place a minimal mapping to get going, then replace it with the proper one once the proper one is buildable.

## Landing in the kernel

The 64-bit entry stub finishes the handoff:

*Listing 4.5. `kernel/kernel_entry.asm`, lines 51–74: settling into 64-bit C.*

```asm
[BITS 64]
long_mode:
    mov ax, 0x10                ; data selector into the segment regs
    mov ds, ax
    mov es, ax
    mov fs, ax
    mov gs, ax
    mov ss, ax

    mov rsp, 0x90000            ; set up a kernel stack

    ; Zero the .bss section. objcopy stripped it out of the binary,
    ; so the memory contents are undefined; clear them.
    extern __bss_start
    extern __bss_end
    mov   rdi, __bss_start
    mov   rcx, __bss_end
    sub   rcx, rdi
    shr   rcx, 3                ; bytes -> qwords
    xor   rax, rax
    cld
    rep stosq

    call kernel_main
```

Zeroing `.bss` matters: C assumes uninitialised globals are zero, but the flat binary the bootloader loaded does not include the `.bss` bytes at all (they would just be zeros on disk, so `objcopy` omits them). The kernel must clear that region itself before any C code that touches a global runs.

## The big picture

```text
real mode --A20+GDT--> protected mode --tables+PAE+LME+PG--> long mode --> kernel_main()
```

It is a lot of one-time ceremony, but it is *fixed*. You set it up once and never think about it again. From `kernel_main()` onward, you are writing normal C.

When something goes wrong, the last printed character tells you exactly which stage failed. This single discipline is responsible for a remarkable share of debugged real-hardware boots.

   *Hint:* Writing to VGA in 32-bit code is `mov word [0xB8000], 0x0F33` (yellow-on-black `3`). In 64-bit code, the same write works once you have set up the segment registers in Listing 4.5.

2. **Read a control register from C.** Once `kernel_main` is reached, declare and call a small inline-asm helper that reads `cr0` and prints it as hex. Verify bit 0 (PE) and bit 31 (PG) are set, and bit 1 (MP) is the default. You have now confirmed, from C, that the mode-switch ritual worked.

   *Hint:* Use the `read_cr0` helper from `kernel/io.h` (you will meet it in the next chapter). For now, the inline assembly is `uint64_t v; __asm__ volatile("mov %%cr0, %0" : "=r"(v));`.

3. **Map an extra page.** Modify the bootstrap page tables in `kernel_entry.asm` to map a second 2 MiB region: say, virtual address `0x200000` to physical `0x200000`.    *Hint:* PD[1] (i.e. `[0x72008]`) maps virtual `0x200000`–`0x3FFFFF`. Set it to `0x00200083` to point at physical `0x200000` with PS+W+P. You will not need to change CR3, but you should `invlpg` the new region, or just reload CR3, to flush any stale TLB.

4. **Trigger a triple fault on purpose, *then* a recoverable fault.** After landing in `kernel_main`, write a wild address: `*((volatile uint32_t*)0xDEADBEEF0000) = 1;`. You will see QEMU reboot. That is a triple fault: no exception handler, so the CPU escalates to reset. Save your output. Then re-read Chapter 6 once you have the IDT in place, and run the same line again; this time you should see a panic dump. The difference is the difference between "the machine is broken" and "the OS told me what happened."

   *Hint:* If your kernel never reaches `kernel_main` because of the wild write, double-check it is *after* your `console_init()` call so you have at least printed a banner first. Otherwise you will be left guessing whether it triple-faulted before or during the write.

# Chapter 5. Your first C kernel: freestanding code and output

You have reached `kernel_main()` in 64-bit mode. From here, you write C, but a special kind: **freestanding C**, with no standard library. This chapter covers how that code is built and linked, how to get text on the screen so you can *see* what your kernel is doing, and how to set up the two output channels every embedded kernel needs.

## There is no libc; you are the library

On bare metal there is no `printf`, no `malloc`, no `strlen`. If you want them, you write them. NexusOS keeps a tiny `kernel/string.c` with `memset`, `memcpy`, `memcmp`, `strlen`, and number-to-string helpers; that is the entire "standard library" for the kernel. Keep these minimal; add functions only when you need them.

The compiler can still *assume* a few of these exist (for instance, it may emit a call to `memcpy` for a struct copy), which is why we provide them and pass `-fno-builtin`. If you ever see a link error for `memset` or `memcpy`, that is the compiler quietly turning a loop into a library call.

## Port I/O: `inb` and `outb`

Devices like the serial port, the timer, and the keyboard are not memory-mapped; they live behind **I/O ports**, accessed with the `in` and `out` instructions. Wrap them in inline assembly once, and the rest of the kernel can call them like ordinary functions.

*Listing 5.1. `kernel/io.h`, lines 7–32: the four port-I/O primitives and a stall.*

```c
static inline void outb(uint16_t port, uint8_t val) {
    __asm__ volatile ("outb %0, %1" : : "a"(val), "Nd"(port));
}

static inline uint8_t inb(uint16_t port) {
    uint8_t ret;
    __asm__ volatile ("inb %1, %0" : "=a"(ret) : "Nd"(port));
    return ret;
}

static inline void outw(uint16_t port, uint16_t val) {
    __asm__ volatile ("outw %0, %1" : : "a"(val), "Nd"(port));
}

static inline uint16_t inw(uint16_t port) {
    uint16_t ret;
    __asm__ volatile ("inw %1, %0" : "=a"(ret) : "Nd"(port));
    return ret;
}

/* A short stall used to give slow legacy hardware (8259 PIC) time
 * to latch a command before the next I/O. Writing to an unused port
 * is the traditional trick. */
static inline void io_wait(void) {
    outb(0x80, 0);
}
```

You will use these constantly. The `"Nd"` constraint allows either an immediate port number or `dx`, which is what the `out` and `in` instructions take. The `"a"` constraint pins the value to `al`/`ax`, which is what the instructions require.

## The linker script: where your kernel lives

The bootloader loaded the kernel to physical `0x10000`, so the linker must place code expecting to execute at that address. A linker script (`kernel/linker.ld`) tells `ld` exactly how to lay out the sections:

*Listing 5.2. `kernel/linker.ld`, complete: where each section of the kernel lives in memory.*

```ld
OUTPUT_FORMAT("elf64-x86-64")
ENTRY(_start)

SECTIONS
{
    . = 0x10000;

    .text ALIGN(16) : {
        *(.text._start)
        *(.text)
        *(.text.*)
    }

    .rodata ALIGN(16) : {
        *(.rodata)
        *(.rodata.*)
    }

    .data ALIGN(16) : {
        *(.data)
        *(.data.*)
    }

    .bss ALIGN(16) : {
        __bss_start = .;
        *(.bss)
        *(.bss.*)
        *(COMMON)
        __bss_end = .;
    }

    . = ALIGN(4096);
    __kernel_end = .;

    /DISCARD/ : {
        *(.comment)
        *(.note*)
        *(.eh_frame*)
    }
}
```

Three details worth absorbing:

- `*(.text._start)` is listed *before* `*(.text)`, so `_start` (in our assembly entry stub) lands at exactly `0x10000`, the address the bootloader jumps to. If `_start` ended up anywhere else, the kernel would die on its first instruction.
- `__bss_start` and `__bss_end` are exported so the entry stub (Listing 4.5) can zero that range before C runs.
- `__kernel_end` is exported so the memory manager (Chapter 7) knows where the kernel image ends and free memory begins.

After linking, `objcopy -O binary` strips the ELF wrapper to a flat binary that the bootloader can load verbatim.

## Output channel 1: VGA text mode

The simplest possible screen output is **VGA text mode**: a fixed 80×25 grid of character cells living at physical address `0xB8000`. Each cell is two bytes: an ASCII code in the low byte and a colour attribute in the high byte. Write to that array, and characters appear instantly:

```c
volatile uint16_t *vga = (uint16_t *)0xB8000;
vga[0] = (uint16_t)'H' | (0x0F << 8);    /* 'H', white-on-black */
```

The `volatile` is essential: it forbids the compiler from caching reads or coalescing writes; both reasonable optimisations against ordinary memory, both wrong for a memory-mapped device.

NexusOS wraps the raw writes in `kernel/console.c` with a cursor, newline handling, backspace handling, and scrolling. When the cursor reaches the bottom of the screen, every row shifts up by one and the last row is cleared.

## Output channel 2: the serial port

VGA is great while you can see the screen, but when you run headless (in CI, on a server, or when you have just broken your graphics driver), the **serial port** is invaluable. COM1 lives at I/O port `0x3F8`. You configure it once for 115200 baud, 8 data bits, no parity, 1 stop bit, and then poll a status bit before sending each byte.

*Listing 5.3. `kernel/console.c`, lines 8–29: configuring COM1 and writing a byte.*

```c
#define COM1            0x3F8

static void serial_init(void) {
    outb(COM1 + 1, 0x00);       /* disable interrupts */
    outb(COM1 + 3, 0x80);       /* DLAB on */
    outb(COM1 + 0, 0x01);       /* divisor low  -> 115200 baud */
    outb(COM1 + 1, 0x00);       /* divisor high */
    outb(COM1 + 3, 0x03);       /* 8N1, DLAB off */
    outb(COM1 + 2, 0xC7);       /* FIFO on, clear, 14-byte threshold */
    outb(COM1 + 4, 0x0B);       /* IRQs enabled, RTS/DSR set */
}

static void serial_putc(char c) {
    while (!(inb(COM1 + 5) & 0x20)) { }     /* wait until TX buffer empty */
    outb(COM1, (uint8_t)c);
}
```

Run QEMU with `-serial stdio` and your kernel's output appears in your terminal. This is the single most useful debugging tool in early kernel work. NexusOS's `console_putc` writes to **both** the serial port and the screen, so you always have a log even if the display goes dark.

## A minimal `kernel_main`

Put it all together and you have something to compile:

```c
void kernel_main(void) {
    console_init();
    console_puts("Hello from the kernel!\n");
    for (;;) __asm__ volatile ("hlt");   /* idle forever */
}
```

Build, `make run`, and you should see your greeting on both serial and screen. That is a 64-bit kernel printing output, which is a real milestone. Stop and let it sit for a minute. *The CPU you started in 16-bit mode is now running C in 64-bit mode and talking to two devices.* The next thing it learns to do is react to events.

## A good habit: print your progress

As you add subsystems, print one line as each comes up:

```text
[boot]  console ready
[boot]  idt installed
[pmm]   total = 255 MiB, free = 254 MiB
[heap]  base=0x200000000 size=131072 B
[sched] init, idle task id=0
```

This "boot log" is exactly how NexusOS reports progress, and when something hangs, the *last line printed* tells you which subsystem to suspect. Cheap to add, priceless to have. By Chapter 12 you will be grateful you got into this habit.

You now have a kernel that talks. The next chapter teaches it to listen, to the timer, the keyboard, and its own mistakes.

## Exercises

1. **Write a tiny `printf` in 30 lines.** Implement `kprintf(const char *fmt, ...)` that handles `%s`, `%d`, `%x`, and `%c`. Use `__builtin_va_list` and friends (they are available in freestanding mode; they are just types in `stdarg.h` which works without libc). It will be the workhorse for every subsystem you add from now on.

   *Hint:* The trick is to walk the format string, copy literal characters through to `console_putc`, and when you hit a `%`, dispatch on the next character. For `%d`, divide by ten repeatedly into a buffer and print the digits in reverse. For `%x`, mask out 4 bits at a time. Do not bother with `%f`; you do not have float on bare metal yet (the SSE registers were turned off in Chapter 2).

2. **Add backspace handling to the VGA console.** The framebuffer console in Chapter 10 already does this, but the VGA console should too: on receiving `\b`, move the cursor back one position and overwrite the previous cell with a space. This is one of the bugs Chapter 12 will explain NexusOS shipped with: a one-line fix that you only find on real text-mode hardware.

   *Hint:* The cursor is a single integer (`vga_cursor` in `console.c`). On `'\b'`, do `if (vga_cursor > 0) vga_cursor--;` then write a space and decrement again so the cursor sits over the cleared cell.

3. **Make the screen scroll.** When the cursor reaches `80 × 25`, shift every row up by one and clear the bottom row. The naive version is a double loop over 80×24 cells; fine for VGA, where the buffer is 4 KB. Time it (a coarse loop count is enough) and compare to a `memcpy`-based version; you will see the cost of doing things "manually" before you have a library.

   *Hint:* The classic loop in `kernel/console.c` is `for row 1..H-1: for col 0..W-1: VGA[(row-1)*W+col] = VGA[row*W+col]`. Once you have a `memmove` helper, the same operation collapses to one call.

4. **Mirror everything to serial too.** Make `console_putc` write the byte to *both* the screen and COM1. Then run `qemu-system-x86_64 -serial stdio` and confirm your boot log appears in both places. From here on, every chapter assumes you have this dual-output property, and Chapter 12 explains why it is the single most important debugging decision you will make.

   *Hint:* The order does not matter, but write to serial first; if the VGA write somehow faults (e.g. the framebuffer is unmapped in a later chapter), the serial copy is already out the door.

Next we will make the kernel respond to events: the timer ticking, keys being pressed. That means handling **interrupts**.
