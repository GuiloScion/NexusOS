# Chapter 8. Multitasking: a scheduler and synchronization

A single thread of execution can only do one thing. To run a shell *and* background work *and*, later, multiple programs, the kernel needs **multitasking**: the illusion that several tasks run at once on one CPU. The trick is to switch between them so fast it looks simultaneous. This chapter builds a scheduler and the locks that make sharing data between tasks safe.

## What a "task" is

A task (or thread) is really just three things: a **saved set of registers** (including the instruction pointer and stack pointer), its **own stack**, and bookkeeping for what state it is in (runnable, blocked, sleeping). To run a task, you load its registers; to pause it, you save them. Switching tasks is exactly: save the current registers, load another's.

*Listing 8.1. `kernel/sched.h`, lines 21–38: the task control block and the four states it can be in.*

```c
typedef enum {
    TASK_RUNNABLE = 0,
    TASK_SLEEPING = 1,
    TASK_BLOCKED  = 2,
    TASK_ZOMBIE   = 3,
} task_state_t;

typedef struct task {
    uint64_t       saved_rsp;
    void          *stack_base;
    uint64_t       stack_size;
    uint64_t       id;
    const char    *name;
    task_state_t   state;
    uint64_t       wake_tick;     /* for SLEEPING tasks; 0 otherwise */
    struct task   *next;          /* circular runnable ring          */
    struct task   *wait_next;     /* sync primitive waiter list      */
} task_t;
```

Two link pointers, not one: `next` threads every task into the circular ring the scheduler walks, while `wait_next` threads a task into a *mutex's* or *semaphore's* waiter queue when it is blocked. A task can only ever be in one waiter queue at a time, so one extra pointer suffices.

## The context switch

The heart of multitasking is a tiny assembly routine that saves the callee-saved registers onto the current stack, swaps the stack pointer to the next task, and `iretq`s into *its* registers. Because the instruction pointer is part of what gets saved and restored (via the return address on the stack), when you "return" you are suddenly running the *other* task. It feels like magic the first time; it is really just careful stack manipulation.

*Listing 8.2. `kernel/sched_switch.asm`, complete: 18 instructions, no return.*

```asm
section .text
bits 64
global _switch_to

_switch_to:
    mov     rsp, rdi
    pop     r15
    pop     r14
    pop     r13
    pop     r12
    pop     r11
    pop     r10
    pop     r9
    pop     r8
    pop     rdi
    pop     rsi
    pop     rbp
    pop     rbx
    pop     rdx
    pop     rcx
    pop     rax
    add     rsp, 16        ; discard saved vector + error_code
    iretq
```

The argument `rdi` is the new task's saved stack pointer. After the `mov rsp, rdi`, we are now executing on the new task's stack. The pops reverse the order in which the IDT stub saved registers when *that* task was last interrupted, the `add rsp, 16` skips the synthetic vector and error-code slots, and the `iretq` pops `rip`, `cs`, `rflags`, `rsp`, `ss` and lands in the new task's code. The same routine works for the very first context switch into a new task; you just have to fake the new task's stack so that this exact pop sequence produces the desired `rip` and an empty register file.

## Creating a task

`task_create` allocates a stack, manufactures a fake initial saved frame so the first switch "returns" into the task's entry function, then splices the new task into the ring.

*Listing 8.3. `kernel/sched.c`, lines 54–88: building a new task from scratch.*

```c
task_t *task_create(const char *name, task_entry_t entry) {
    task_t  *t     = (task_t  *)kmalloc(sizeof(task_t));
    if (!t) return NULL;
    uint8_t *stack = (uint8_t *)kmalloc(KSTACK_SIZE);
    if (!stack) { kfree(t); return NULL; }

    interrupt_frame_t *f = (interrupt_frame_t *)
        (stack + KSTACK_SIZE - sizeof(interrupt_frame_t));
    memset(f, 0, sizeof(*f));
    f->rip    = (uint64_t)entry;
    f->cs     = KERNEL_CS;
    f->rflags = RFLAGS_BASE;
    f->rsp    = (uint64_t)(stack + KSTACK_SIZE);
    f->ss     = KERNEL_SS;

    t->saved_rsp  = (uint64_t)f;
    t->stack_base = stack;
    t->stack_size = KSTACK_SIZE;
    t->id         = next_id++;
    t->name       = name;
    t->state      = TASK_RUNNABLE;
    t->wake_tick  = 0;
    t->wait_next  = NULL;

    cli();
    t->next       = current->next;
    current->next = t;
    sti();
    return t;
}
```

The cute trick is in the middle: we build an `interrupt_frame_t` at the *top* of the new stack with `rip` set to the entry function, `cs`/`ss` set to the kernel selectors, and `rflags` set so that interrupts are enabled (`IF=1`). The first time `_switch_to` runs against this task, the `iretq` pops that frame and jumps into `entry`, exactly as if the task had been preempted at the moment before its first instruction.

## Scheduling policy: round-robin

*Which* task runs next? The simplest fair policy is **round-robin**: cycle through runnable tasks, giving each a turn. NexusOS keeps a circular list of tasks and, on each scheduling decision, picks the next runnable one. (Sleeping and blocked tasks are skipped; sleeping tasks are returned to `RUNNABLE` when their wake tick is reached.)

Two ways a switch happens:

- **Cooperative.** A task calls `sched_yield()` to voluntarily give up the CPU. Under the hood this is `int $0x80`, a software interrupt, which routes through the dispatcher in Chapter 6 straight to `scheduler_tick`.
- **Preemptive.** The **timer interrupt** fires (IRQ0) and the handler forces a switch, so even a task that never yields cannot hog the CPU. This is why the PIT heartbeat from Chapter 6 matters; a kernel without one is cooperative-only.

`sched_sleep_ms()` puts the current task into `TASK_SLEEPING` with a wake-tick computed from `pit_ticks()`, then yields. On every tick, the scheduler walks the ring waking any sleeper whose deadline has passed.

## The hard part: shared data and races

The moment two tasks (or a task and an interrupt) touch the same variable, you have a **race condition**. Classic example: two tasks both do `counter++`. That is really *read, add, write*; if a switch happens between the read and the write, an update can be lost, and `counter` ends up wrong.

You need **mutual exclusion**: a way to say "only one task in this critical section at a time."

## Synchronization primitives

NexusOS provides three, all built on the scheduler's `BLOCKED` state and the `int $0x80` yield path. Reading them as a set is the cleanest way to internalise how kernel-side locks actually work.

*Listing 8.4. `kernel/sync.c`, lines 26–69: the mutex, with hand-off on unlock.*

```c
void mutex_init(mutex_t *m) {
    m->locked    = false;
    m->owner     = NULL;
    m->wait_head = NULL;
}

void mutex_lock(mutex_t *m) {
    task_t *self = sched_current();

    cli();
    if (!m->locked) {
        m->locked = true;
        m->owner  = self;
        sti();
        return;
    }
    self->wait_next = NULL;
    if (!m->wait_head) {
        m->wait_head = self;
    } else {
        task_t *t = m->wait_head;
        while (t->wait_next) t = t->wait_next;
        t->wait_next = self;
    }
    self->state = TASK_BLOCKED;
    sti();
    sched_yield();
}

void mutex_unlock(mutex_t *m) {
    cli();
    if (m->wait_head) {
        task_t *t       = m->wait_head;
        m->wait_head    = t->wait_next;
        t->wait_next    = NULL;
        m->owner        = t;
        t->state        = TASK_RUNNABLE;
    } else {
        m->locked = false;
        m->owner  = NULL;
    }
    sti();
}
```

Two implementation tricks. First, on a single CPU, the only thing that could preempt the lock's state update is the timer interrupt, so wrapping the small critical region in `cli()` / `sti()` makes it atomic with respect to scheduling. Second, on unlock with waiters, NexusOS uses **hand-off**: it transfers ownership directly to the next waiter rather than clearing `locked` and letting a race decide. This eliminates a class of unfair-wakeup bugs at the cost of slightly more code in `unlock`.

The **semaphore** generalises the mutex to a counter, useful for producer/consumer patterns, and for an interrupt to wake a task (the disk driver in Chapter 9 will use one):

*Listing 8.5. `kernel/sync.c`, lines 73–112: counting semaphore.*

```c
void sem_wait(semaphore_t *s) {
    task_t *self = sched_current();

    cli();
    if (s->count > 0) {
        s->count--;
        sti();
        return;
    }
    self->wait_next = NULL;
    if (!s->wait_head) {
        s->wait_head = self;
    } else {
        task_t *t = s->wait_head;
        while (t->wait_next) t = t->wait_next;
        t->wait_next = self;
    }
    self->state = TASK_BLOCKED;
    sti();
    sched_yield();
}

void sem_post(semaphore_t *s) {
    cli();
    if (s->wait_head) {
        task_t *t    = s->wait_head;
        s->wait_head = t->wait_next;
        t->wait_next = NULL;
        t->state     = TASK_RUNNABLE;
    } else {
        s->count++;
    }
    sti();
}
```

A **condition variable** lets a task wait for a condition to become true, atomically releasing a mutex while it sleeps. NexusOS's implementation is in the same file; the trick is that `cond_wait` inlines `mutex_unlock` so the "release lock, go to sleep" pair is atomic with respect to other tasks.

## Proving it works

How do you *know* your locking is correct? **Test the invariant.** NexusOS runs two demo tasks that each increment their own private counter and a shared one under a mutex. The invariant: `counter_a + counter_b == shared` (give or take one if sampled mid-update). The `tasks` shell command shows it live:

```text
switches:     1273302
counter_a:    144426
counter_b:    144425
shared:       288851
a+b - shared: 0          <- if this stays 0, the mutex held
```

Seeing that hold after a million context switches, including on real hardware, is real evidence your scheduler is fair and your locks are sound. Build a test like this; it catches the kind of subtle bug that "it seemed to work" never will.

## Where this leads

With multitasking, the kernel can run a shell as the idle task while background work proceeds, and (Chapter 11) a compositor task can redraw the screen independently. It is also the foundation for real **processes** later (Chapter 13). A process is a task plus its own address space and privilege level.

## Exercises

1. **Two tasks, one shared counter, no lock.** Create two tasks that each loop a million times incrementing a shared `static volatile uint64_t shared = 0`. Each task also keeps a private counter and adds one to it per iteration. After both finish, print `counter_a + counter_b` and `shared`. They should be equal, but without a lock, they will not be. Welcome to your first observed race.

   *Hint:* Use `sched_yield()` inside the loop to force the scheduler to switch frequently. Without yields the timer's 10 ms tick may rarely catch the increment mid-flight, hiding the race. You want the race to be loud.

2. **Add a mutex; verify the invariant holds.** Wrap the increment in `mutex_lock(&m) / mutex_unlock(&m)`. Re-run; `a + b == shared` should hold across the entire run. This is your locking proof. Leave the test in the tree as a regression check: every time you touch the scheduler, this is the first thing to re-run.

   *Hint:* The mutex must be `static` and zero-initialised, or initialised via `mutex_init`. A stack-local mutex is a bug factory: each task allocating its own does nothing useful.

3. **Make a sleeping task.** Write a task that prints a banner, calls `sched_sleep_ms(1000)`, prints a different banner, and exits. With other tasks running, you should see the banner pause for a second of *real time*, not "the scheduler did a million switches." This is the difference between busy-waiting and properly blocking, and it is the foundation of every periodic background job.

   *Hint:* The sleep is in milliseconds, but the PIT runs at 100 Hz, so the resolution is 10 ms. A `sched_sleep_ms(1)` sleeps either 0 or 10 ms depending on timing; do not rely on shorter sleeps being accurate.

4. **Build a producer/consumer with one semaphore.** A producer task writes one element per loop into a fixed-size ring buffer, then `sem_post`s; a consumer `sem_wait`s and reads one element. Verify total produced == total consumed and that the consumer naturally throttles to the producer's rate. This is the same pattern Chapter 9's disk driver uses to wait for the IRQ.

   *Hint:* Initialise the semaphore to zero (no items available). The buffer itself needs a separate mutex if you want multiple producers, but with one producer and one consumer the head/tail indices can be `volatile` and avoid locking, which is a classic SPSC (single-producer/single-consumer) ring.

# Chapter 9. Storage: talking to a disk and reading a filesystem

A useful OS can read files. That is two layers: a **disk driver** that moves raw sectors to and from the hardware, and a **filesystem** that interprets those sectors as files and directories. We will do both at the simplest useful level: a PIO ATA driver and read-only FAT12.

## Layer 1: the disk driver (ATA PIO)

Old-style IDE/ATA disks are controlled through I/O ports. The simplest transfer mode is **PIO** (Programmed I/O): the CPU itself moves the data, word by word, through a data port. Slow, but dead simple, and perfect for learning.

The primary ATA channel lives at ports `0x1F0–0x1F7`. To read a sector you wait for the drive to be ready, write the LBA and a sector count, issue the `READ SECTORS` command (`0x20`), wait again for data to be available, then read 256 16-bit words from the data port. NexusOS does this **interrupt-driven**: instead of busy-waiting for the read to complete, it blocks on a semaphore that the IRQ14 handler posts when the disk signals ready.

*Listing 9.1. `kernel/ata.c`, lines 156–195: the sector read, blocking on a completion semaphore.*

```c
bool ata_read_sector(uint32_t lba, void *buf) {
    if (!initialized) return false;
    if (lba >> 28)     return false;   /* 28-bit LBA only */

    mutex_lock(&io_lock);

    if (!wait_not_busy()) { mutex_unlock(&io_lock); return false; }

    outb(REG_DRIVE,    (uint8_t)(DRIVE_SLAVE_LBA | ((lba >> 24) & 0x0F)));
    ata_400ns_delay();
    outb(REG_SECCOUNT, 1);
    outb(REG_LBA0,     (uint8_t)( lba        & 0xFF));
    outb(REG_LBA1,     (uint8_t)((lba >>  8) & 0xFF));
    outb(REG_LBA2,     (uint8_t)((lba >> 16) & 0xFF));
    outb(REG_COMMAND,  CMD_READ_SECTORS);

    /* Block until IRQ14 says the sector buffer is ready. */
    sem_wait(&io_done);

    /* The interrupt only tells us the controller asserted INTRQ; the drive
     * may still have BSY set briefly. Wait for it to clear before trusting
     * the DRQ/ERR bits. */
    wait_not_busy();

    uint8_t status = inb(REG_STATUS);
    if (status & ST_ERR) {
        mutex_unlock(&io_lock);
        return false;
    }
    if (!(status & ST_DRQ)) {
        mutex_unlock(&io_lock);
        return false;
    }

    uint16_t *p = (uint16_t *)buf;
    for (int i = 0; i < 256; i++) p[i] = inw(REG_DATA);

    mutex_unlock(&io_lock);
    return true;
}
```

This is a precise dance and worth re-reading once: the `mutex_lock` serialises commands to the controller (only one outstanding command at a time); the `400 ns` delay after selecting the drive is the standard "read alt status four times" trick to give the controller time to settle; the `sem_wait` is where the calling task *sleeps*. IRQ14 wakes it via `sem_post`, exactly the producer/consumer use of semaphores from Chapter 8.

### Two bugs worth knowing

These are real lessons from building NexusOS:

- **Wait for `BSY` to clear *after* the completion interrupt** before reading the data or status. The interrupt only means "I have something to say"; the drive may still be momentarily busy. Trusting the status too early reads garbage. The `wait_not_busy()` after `sem_wait` is exactly this guard.
- **Handle a missing drive.** On real hardware with no legacy IDE disk, the bus "floats" and the status register reads `0xFF`, which has the `BUSY` bit set, so a naive `while (busy)` loop **hangs forever**. Treat `0xFF` (and `0x00`) as "no device" and bound your wait loops with a counter. NexusOS does this in `ata_init`:

*Listing 9.2. `kernel/ata.c`, lines 119–135: detect a missing drive and bail.*

```c
    uint8_t s = inb(REG_STATUS);
    /* 0x00 = nothing there; 0xFF = floating bus (no controller/device,
     * e.g. a real machine whose disk is SATA/AHCI, not legacy IDE).
     * Either way, there is no drive to talk to. */
    if (s == 0 || s == 0xFF) {
        console_puts("[ata] no device on primary channel\n");
        return false;
    }

    /* Wait for BSY -- but bounded. An absent device leaves the bus
     * reading 0xFF (BSY always set), which would otherwise hang. */
    int spin = 1000000;
    while ((inb(REG_STATUS) & ST_BSY) && --spin) { }
    if (spin == 0) {
        console_puts("[ata] timeout; no usable device\n");
        return false;
    }
```

These kinds of defensive checks are the difference between "works in the emulator" and "works on a real machine." Chapter 12 has the broader story.

## Layer 2: the filesystem (FAT12)

Raw sectors are not files. A **filesystem** is the on-disk format that organises them. **FAT12** (the old floppy format) is the gentlest one to implement and is trivially creatable on your host with `mtools`. Ideal for learning. A FAT12 disk has four regions, described by the **BPB** (BIOS Parameter Block) in sector 0:

```text
[ boot sector / BPB ][ FAT(s) ][ root directory ][ data area (clusters) ]
```

To read a file, NexusOS's `kernel/fat.c` does three things:

1. Parse the BPB to find where each region starts and how big it is.
2. Scan the **root directory** (an array of 32-byte entries) for the filename, in the old "8.3" format (`HELLO   TXT`).
3. The entry gives the file's **first cluster**. Follow the **FAT chain** (a linked list where `FAT[n]` tells you the cluster after `n`) reading each cluster's sectors until you hit the end-of-chain marker.

The on-disk directory entry is a fixed 32-byte struct:

*Listing 9.3. `kernel/fat.c`, lines 53–62: the on-disk directory entry.*

```c
typedef struct PACKED {
    char     name[8];
    char     ext[3];
    uint8_t  attr;
    uint8_t  reserved[10];
    uint16_t mtime;
    uint16_t mdate;
    uint16_t first_cluster;
    uint32_t size;
} dirent_t;
```

FAT12 has one quirk worth showing in code: each FAT entry is **12 bits**, packed so that two consecutive entries share a byte. The extraction is a small bit-twiddle:

*Listing 9.4. `kernel/fat.c`, lines 96–105: extracting a 12-bit FAT entry.*

```c
static uint16_t fat12_next(uint16_t cluster) {
    uint32_t off = (uint32_t)cluster * 3 / 2;
    uint16_t v;
    if (cluster & 1) {
        v = (uint16_t)((fat_cache[off] >> 4)
                       | ((uint16_t)fat_cache[off + 1] << 4));
    } else {
        v = (uint16_t)(fat_cache[off]
                       | ((uint16_t)(fat_cache[off + 1] & 0x0F) << 8));
    }
    return v & 0xFFF;
}
```

That is enough to back `ls` (walk the root directory) and `cat <file>` (read the cluster chain), which is exactly what NexusOS's shell exposes.

## Building a disk image to test with

You do not need a real disk. `mtools` builds a FAT image on your host with no root permission required:

```sh
dd if=/dev/zero of=fat.img bs=1024 count=1440   # a 1.44 MB "floppy"
mformat -i fat.img -f 1440 ::                   # format it FAT12
mcopy -i fat.img hello.txt ::HELLO.TXT          # copy a file in
```

Attach the image to QEMU as a second drive (NexusOS's `Makefile` does all this and mounts it on the second ATA channel) and your `ls` should show `HELLO.TXT`.

## Toward a real filesystem layer

FAT12 read-only is a great start. The natural next steps (Chapter 13):

- **Write support.** Allocate clusters in the FAT, update the FAT, write the data. The hard part is keeping multiple in-flight writes consistent; this is the same problem the kernel `fsync` operation solves.
- **A VFS** (Virtual File System) layer: an abstraction so the rest of the kernel says `open` / `read` / `write` without caring whether the backing store is FAT, ext2, or a network share.
- **Better drivers.** AHCI/SATA and NVMe for modern disks; PIO ATA only reaches legacy controllers, and as Chapter 12 will show, those controllers are nowhere on most current machines.

For now you can store and read files, and that is a satisfying capability to have built from port pokes and sector math.

You now have persistent storage. The next chapter spends those bytes on pixels.

## Exercises

1. **Read sector 0 by hand.** Skip the filesystem entirely. Call `ata_read_sector(0, buf)`, then print `buf[510]` and `buf[511]`. They should be `0x55` and `0xAA` (the boot signature). Now you have proven your driver works without depending on the filesystem code at all. Bisecting any future "I cannot read files" bug starts here.

   *Hint:* Use `console_put_hex(buf[510])` and `console_put_hex(buf[511])`. If you see `0xFF` and `0xFF`, the driver returned without filling the buffer; go re-check the `ST_DRQ` test.

2. **Print the BPB.** Read sector 0, then print bytes 11–12 (`bytes_per_sector`), 13 (`sectors_per_cluster`), 14–15 (`reserved_sectors`), 16 (`num_fats`), 17–18 (`root_entries`), and 22–23 (`sectors_per_fat`). Compare to what `mformat` told you. You have just decoded a real on-disk header.

   *Hint:* These are all little-endian. `bytes_per_sector` is at offset 11 because the BPB starts 3 bytes into the boot sector (after the initial jump). The C struct is fine; just `memcpy` and dereference.

3. **Walk the FAT chain.** Pick a file from your image. Look up its directory entry, read its `first_cluster`, then follow `fat12_next` until you hit a value ≥ `0xFF8` (end of chain). Print each cluster number. For a small file you should see one or two clusters; for a larger one, a chain.

   *Hint:* Cluster numbers below 2 are reserved (`0` = free, `1` = unused). The data area starts at cluster 2. Always validate the chain length; a corrupted FAT can cycle forever otherwise.

4. **Implement `cat` end-to-end.** Combine the previous exercises: take a filename, find its directory entry, follow the cluster chain, and `console_puts` each cluster's bytes up to the file's total `size`. Watch out for the file ending mid-cluster: read the full cluster but only print as many bytes as `size` says remain. This is exactly NexusOS's shell `cat` command.

   *Hint:* The conversion from a cluster number to a sector is `data_start + (cluster - 2) * sectors_per_cluster`. Keep a running byte counter against `size` so you stop on the right boundary, not at the next cluster.
